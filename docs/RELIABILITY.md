# Надёжность Java Collections Visualizer

> **Статус:** инженерные принципы и план развития, а не подтверждение production-SLA.
> **Аудитория:** разработчики, архитекторы и участники ревью.
> **Масштаб сейчас:** небольшая публичная учебная демонстрация для знакомых.
> **Последняя сверка:** 2026-11-08; перед изменениями проверяйте фактический код, конфигурацию и версию релиза.

## 1. Цель и область применения

Визуализатор должен объяснять фундаментальные алгоритмы Java-коллекций,
оставаться доступным при обычных ошибках пользователя и безопасно отказывать
при перегрузке, не влияя на другие приложения того же VDS.

Приоритеты: **корректность алгоритма и состояния → понятные ошибки →
ограниченность потребления ресурсов → измеримость → масштабирование по фактам**.

В этой фазе не вводим Redis, PostgreSQL, Kafka, Kubernetes, распределённые
сессии или WebSocket ради самого факта их использования. Сначала измеряем.

## 2. Что уже реализовано (проверять по текущему коду)

- **Java 21 core** исполняет инструментированные HashMap и ArrayList и формирует
  события и снимки. React лишь воспроизводит полученный trace; навигация
  по кадрам не отправляет дополнительных команд в Java.
- **Один Spring Boot процесс:** \`SessionStore\` хранит экземпляры движков в
  \`ConcurrentHashMap<UUID, Session>\`. Внутри сессии операции сериализованы
  блокировкой, а \`revision\` обнаруживает конфликтующие изменения.
- **Ограниченность сессий:** TTL (по умолчанию 1800 секунд), общий лимит
  (в коде по умолчанию 128) и ограничение живых сессий на определённого
  клиента. Эти значения **не равны автоматически действующим на VDS**:
  реальные env и текущий релиз проверяются отдельно.
- **Повторное использование слота:** в реализации для 0.3.1 переключение
  HashMap/ArrayList заменяет движок через \`POST /sessions/{id}/reset\`,
  а не создаёт новый UUID при каждом переключении. Доставка этой версии
  на production **не подтверждается наличием кода в main**.
- **Admission control:** \`ApiAdmission\` и \`ApiLimitFilter\` ограничивают
  частоту создания сессий, частоту работы, число отслеживаемых клиентов и
  одновременные рабочие запросы; HTTP 429 содержит \`Retry-After\`.
  Глобальная одновременная работа по умолчанию ограничена двумя запросами.
- **Размер ответа:** frontend запрашивает compact trace; полный trace
  по умолчанию отключён. API использует сжатие JSON. При этом сложные
  сценарии всё ещё могут создавать объёмные промежуточные данные.
- **Proxy:** \`ClientAddress\` доверяет только явно заданным непосредственным
  IP proxy. Образец Caddy перезаписывает \`X-JCV-Client-IP\` реальным адресом
  входящего клиента. Сам факт наличия файла не доказывает, что работающий
  Caddy загрузил именно этот конфиг.

Детали и установленные ограничения: [API security](API_SECURITY.md),
[архитектура](ARCHITECTURE.md), [расследование сессий](verification/session-lifecycle.md).

## 3. Инварианты надёжности

1. **Одна операция — одно однозначное изменение.** Успешная мутация увеличивает
   \`revision\` один раз. Команды одной сессии не должны исполняться одновременно
   с потерей обновлений; новая коллекция не должна вытеснять уже принятую команду
   из-за устаревшего ответа браузеру.
2. **Не повторять неизвестную мутацию автоматически.** Если ответ потерян,
   результат команды неизвестен: сначала \`GET /sessions/{id}\` и сравнение
   \`revision\`; лишь после восстановления состояния пользователь решает,
   выполнять ли действие снова.
3. **Понятные ошибки.** \`409\` — конфликт версии, получить актуальное состояние;
   \`404\` для истёкшей/отсутствующей сессии — предложить новую; \`429\` —
   объяснить лимит и уважать \`Retry-After\`; \`503 SESSION_LIMIT\` — отсутствие
   доступных слотов, без автоматического шторма попыток.
4. **Безопасность промежуточных снимков.** \`WORKING\` может на короткое время
   показывать невалидные для итогового состояния связи; \`COMMITTED\` обязан
   соблюдать инварианты коллекции. Снимки опубликованного trace не мутируют.
5. **Ограниченные ресурсы.** Значения, число элементов, длина trace, число
   сессий и частота запросов должны оставаться ограниченными. Новые коллекции
   обязаны явно определять наиболее дорогие операции и худшие сценарии.
6. **Изоляция пользователей.** Случайные UUID, изоляция состояния и проверка
   версии не заменяют полноценную авторизацию. IP-квоты — защита от нагрузки,
   но не идентификатор человека: несколько посетителей за NAT делят IP.
7. **Изоляция Friendly Loan.** API слушает loopback за Caddy; лимиты JVM/systemd,
   отдельный сервис и осторожные релизы не должны нарушать работу второго
   приложения на VDS.

## 4. Отказы и восстановление

| Событие | Ожидаемое поведение |
|---|---|
| Перегрузка / 429 | Без мутации, понятное сообщение, пауза; не слать бесконечные retries |
| Конфликт / 409 | Получить актуальный snapshot и revision; не перезаписывать новый UI старым ответом |
| Истечение TTL / 404 | Явно создать новую сессию; показать потерю предыдущего server-side состояния |
| Неизвестен результат POST | Не повторять POST автоматически; сначала запросить состояние |
| Перезапуск JVM | In-memory сессии пропадают; frontend должен восстановить интерфейс новой сессией |
| Недоступен backend / 5xx | Сохранить доступность статического frontend, показать ошибку и возможность восстановления |
| Потеря/перезапуск Caddy | Health и HTTPS проверяются отдельно; откат не должен касаться Friendly Loan |

Регрессионные сценарии и установленный дефект 0.3.0:
[session lifecycle](verification/session-lifecycle.md).
Задача на улучшение UX: [#27](https://github.com/Oleg520/java-collections-vizualizer/issues/27).
Отслеживание расследования и доставки исправления: [#26](https://github.com/Oleg520/java-collections-vizualizer/issues/26).

## 5. Наблюдаемость: минимальный полезный набор

Цель — понимать **почему пользователь получил ошибку**, не собирая его данные.

- Число активных сессий / свободных слотов и количество admission rejections
  с метками **только по ограниченному коду причины**.
- Частота HTTP 409/429/503/5xx, p50/p95 задержки API и число выполняемых команд.
- Размер compact trace, время исполнения и сериализации; отдельно тяжёлые
  resize/treeify и операции по коллекциям.
- Heap, RSS, CPU, GC и число потоков; фоновые рестарты процесса.

**Запрещённые метки/логи:** UUID сессии, пользовательские ключи/значения,
raw trace, IP как высококардинальная метка, секреты, произвольный URL с ID.

Диагностические endpoints должны быть закрыты от интернета: loopback,
надёжный proxy/access control или отсутствие публичного маршрута. Логи
должны быть ограничены по объёму и сроку хранения. Не вводить внешнюю
систему метрик без обоснованной пользы. Задача: [#28](https://github.com/Oleg520/java-collections-vizualizer/issues/28).

Реализованный минимальный набор и его границы описаны в
[backend diagnostics](OBSERVABILITY.md): занятые слоты, допуски/отказы, latency,
размер записанного trace и стандартные JVM metrics. Данные живут в памяти процесса;
историческое хранение, уведомления, отдельное время алгоритма/сериализации и RSS
через Actuator не реализованы. Это не подтверждает настройки работающего VDS.

## 6. Нагрузочные проверки и пределы

Проводить нагрузочные тесты **в изолированном окружении по умолчанию**.
VDS с Friendly Loan — только по отдельному разрешению владельца и после
оценки рисков. Не повышать rate limits, пытаясь замаскировать ошибку
жизненного цикла сессий.

Проверять 1, 5, 10 и 25 виртуальных пользователей: создание, команды,
тяжёлый resize/treeify, переключения коллекций и восстановление после
отказа; сравнивать с настроенными квотами. Фиксировать hardware, настройки
JVM/лимитов, p50/p95, пропускную способность, ошибки, RSS/CPU/GC и
объёмы ответов. **Ожидаемые HTTP 429 не равны падению сервера.**

Текущие профили в [verification/](verification/) — локальные
измерения, не SLA и не доказательство ёмкости текущего VDS.
Задача: [#29](https://github.com/Oleg520/java-collections-vizualizer/issues/29).

## 7. Когда масштабировать

**Сейчас:** один Java backend, локальные сессии, Caddy, Cloudflare Pages, ограничения.
Оптимизировать утечки, повторные создания сессий, объём trace и клиентские
retries до увеличения инфраструктуры.

**Если появились стабильные перегрузки:** сначала подтвердить метриками,
что причина именно в CPU/RAM или количестве слотов, а не в дефекте клиента,
ошибочной идентификации IP за proxy или лимитах конфигурации. Рассмотреть
обоснованное увеличение ресурсов одного JVM-инстанса и лимитов,
не ухудшая изоляцию от Friendly Loan.

**Если одного инстанса действительно недостаточно:** отдельно спроектировать
совместное хранение **состояния движков** и атомарных обновлений по
\`revision\`, распределённые rate limits, балансировку и поведение при
потере инстанса. Redis может помочь с временными данными, но он не
превращает mutable Java engine в распределённую сессию автоматически.
PostgreSQL имеет смысл при появлении учётных записей, сохранённых
упражнений или долговременного прогресса. Kafka и Kubernetes не
являются обязательными шагами роста этого продукта.

Триггер масштабирования — измеренное ухудшение UX/доступности при
реальной аудитории, а **не произвольный прогноз на 1000 пользователей**.

## 8. Проверки при изменениях

- Изменения алгоритма: дифференциальные Java-тесты со стандартной коллекцией,
  свойства/invariants, детерминированные пограничные сценарии.
- Изменения API: контракт, версия, сессии, конфликт revision, rate limits,
  error handling, компактное кодирование и обратная совместимость.
- Изменения frontend: unit-тесты, Playwright desktop/mobile, error/reconnect,
  воспроизведение offline, анимации и accessibility/reduced motion.
- Инфраструктура: отдельный reviewed PR, проверка health, безопасный reload
  Caddy, rollback и отсутствие изменений Friendly Loan.
- Никаких production deployment, release, merge или изменения лимитов без
  отдельного разрешения владельца.

Команды и CI: [testing](TESTING.md), [versioning](VERSIONING.md),
[deployment](../deploy/README.md), [contributing](../CONTRIBUTING.md).
