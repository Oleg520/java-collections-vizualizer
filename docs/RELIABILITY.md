# Надёжность Java Collections Visualizer

Документ описывает реализованные гарантии, ограничения и направления проверок
учебного приложения. Это не SLA. Открытая работа отслеживается в
[GitHub Issues](https://github.com/Oleg520/java-collections-vizualizer/issues).

## Реализованные границы

- Java core исполняет алгоритмы HashMap/ArrayList и публикует неизменяемые
  snapshots. React воспроизводит trace без повторного исполнения команд.
- Один Spring Boot процесс хранит движки в `SessionStore`. Блокировка сессии
  сериализует операции; `revision` обнаруживает конфликтующие изменения.
- Сессии ограничены TTL (1800 секунд по умолчанию), общим пределом (128)
  и квотой на клиента. Переключение коллекции через `/sessions/{id}/reset`
  заменяет движок в том же UUID, не расходуя новый слот.
- Admission control ограничивает частоту создания/работы, число отслеживаемых
  клиентов и одновременные запросы, включая сериализацию ответа. Отказ 429
  содержит `Retry-After`. Запросы не ожидают освобождения рабочего слота.
- Compact trace и JSON compression сокращают ответы. Full trace по умолчанию
  отключён; самые дорогие сценарии всё ещё создают большие промежуточные данные.
- `ClientAddress` доверяет custom-заголовку только от явно заданных непосредственных
  proxy IP. IP-квоты объединяют пользователей за NAT и не являются авторизацией.

Настройки: [API security](API_SECURITY.md). Поведение коллекций и лимиты их
размеров: [архитектура](ARCHITECTURE.md).

## Инварианты и восстановление

1. Успешная мутация увеличивает `revision` один раз. Запоздалый ответ не должен
   перезаписывать новое состояние интерфейса или терять принятую команду.
2. Если ответ POST потерян, результат неизвестен. Клиент сначала получает сессию
   через GET; автоматического повтора мутации нет.
3. `WORKING` snapshots могут показывать промежуточные нарушения итоговых
   инвариантов. `COMMITTED` обязан соблюдать инварианты коллекции; ранее
   опубликованные снимки не меняются.
4. Значения, элементы, trace, сессии и запросы должны оставаться ограниченными.
   Новая коллекция должна определять свои худшие сценарии и ресурсные пределы.
5. Случайные UUID и revision не заменяют авторизацию. В сессиях не следует
   хранить чувствительные данные.

| Событие | Ожидаемое восстановление |
|---|---|
| 429 | Показать лимит, учитывать `Retry-After`, избегать шторма повторов |
| 409 | Получить актуальные snapshot/revision |
| 404 `SESSION_NOT_FOUND` | Предложить новую сессию; предыдущее состояние потеряно |
| Неизвестный HTML/generic 404 | Сохранить UUID, показать ошибку маршрута/совместимости |
| Неизвестен результат POST | GET перед следующим явным действием пользователя |
| Перезапуск JVM | Сессии в памяти теряются; восстановление через новую сессию |
| Недоступен backend | Статический frontend показывает ошибку и возможность восстановления |

[Session lifecycle](verification/session-lifecycle.md) объясняет причину прежнего
накопления сессий, исправление и строгий локальный регрессионный прогон.
Перезагрузка/закрытие вкладки и потерянный ответ создания всё ещё могут оставить
неизвестный клиенту слот до TTL. Постоянного хранилища и распределённых сессий нет.

## Наблюдаемость

[Локальная диагностика](OBSERVABILITY.md) предоставляет занятые слоты,
допуски/отказы, HTTP latency, размер записанного trace и стандартные JVM metrics.
Actuator слушает отдельный loopback-порт; Compose не публикует его.

Метрики имеют ограниченные метки. UUID, ключи/значения пользователя, raw trace,
IP, секреты и URL с ID не должны попадать в custom tags или диагностические логи.
Счётчики живут в памяти процесса и сбрасываются при рестарте. Историческое
хранение, оповещения, отдельное время алгоритма/сериализации и RSS через Actuator
не реализованы. RSS измеряется средствами ОС.

## Нагрузочные проверки

Используйте изолированный локальный backend. Не повышайте лимиты, пытаясь
замаскировать ошибку жизненного цикла сессий. Сравнивайте 1, 5, 10 и 25 виртуальных
пользователей: создание, команды, resize/treeify, переключения и восстановление.
Фиксируйте hardware, JVM, квоты, p50/p95, throughput, ошибки, RSS/CPU/GC и размер
ответов. Ожидаемые HTTP 429 являются работой защиты, а не падением сервера.

[Сохранённые измерения](verification/README.md) — исторические локальные пробы,
не доказательство ёмкости произвольного окружения. Дальнейшие воспроизводимые
нагрузочные проверки отслеживаются в [#29](https://github.com/Oleg520/java-collections-vizualizer/issues/29).

## Развитие по измерениям

Сначала устраняйте утечки, повторные создания, избыточный trace и клиентские
retries. При устойчивой перегрузке определите узкое место: алгоритм, сериализация,
GC, число сессий или CPU. Изменение квот должно сопровождаться измерениями.

Несколько backend-процессов потребуют решения маршрутизации mutable-движков,
атомарных revision, распределённых квот и потери инстанса. Redis сам по себе
не превращает Java engine в распределённую сессию. БД оправдана при появлении
учётных записей или сохранённого прогресса; Kafka/Kubernetes не являются
обязательными шагами роста учебного проекта.

## Проверки изменений

- Алгоритмы: сравнение с JDK, структурные инварианты и пограничные сценарии.
- API: wire-контракт, сессии/revision, ошибки, квоты и compact encoding.
- Frontend: Vitest, Playwright desktop/mobile, восстановление, offline playback,
  accessibility и reduced motion.
- Сборка: точная версия Git, упаковка и неизменность артефактов.
