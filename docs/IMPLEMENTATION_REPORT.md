# Отчёт о реализации и проверке MVP

Дата: **7 ноября 2026**. Локальная ревизия начата с `main` на `8ccaebe`
(`feat: add GitHub source link to app header (#1)`). `origin/main` получена через
fetch и проверена fast-forward merge; локальных изменений перед обновлением не было.
Изменения PR #1 сохранены и проверены E2E.

**MVP HashMap реализован и проверен локально. Публичный деплой не выполнялся.**

## Что уже было и что завершено

В исходной ветке уже работали независимое Java-ядро, Spring Boot API, React UI,
анимация списков/деревьев, основные тесты и конфигурации сборки. Дерево использовало
алгоритмы OpenJDK с сохранёнными лицензиями. Переписывать эти части не потребовалось.

В этой ревизии:

1. Исправлены начальные условия сценариев. `resize` и `why-no-tree` раньше
   наследовали initialCapacity сессии и при 32/64 могли не показать обещанное
   поведение. Теперь все демонстрации задают собственный конструктор; обычный
   RESET сохраняет настройку сессии. CONFIGURED сообщает оба значения.
2. События сравнения разделяют `identityEqual` и фактический `equalsChecked`.
   Совпавший null-ключ не выдаётся за вызов equals.
3. Закреплены проверками лимиты 128 записей / 512 учебных ID, атомарность отказов,
   обновление на заполненной карте и неизменность старых снимков после новых операций.
4. После измерения trace добавлено обратимое компактное представление на границе API.
   Версии узлов передаются в nodePool один раз; каждый снимок содержит абсолютные
   ссылки nodeRefs. Ни одно событие или состояние не отбрасывается. Java-ядро
   по-прежнему не зависит от HTTP, Spring или React. Прежний полный формат API сохранён.
5. Frontend разрешает ссылки в снимки с общими неизменяемыми версиями узлов.
   Это уменьшает объём JSON и память истории; HashMap-алгоритм в TypeScript не появился.
6. Включён gzip для JSON. Параллелизм Tomcat ограничен восемью рабочими потоками
   (HTTP_THREADS), 64 соединениями и очередью 32; проверен запуск с heap 256 MiB.
7. SVG остаётся смонтированным при удалении последнего узла, позволяя завершить
   exit-анимацию. Устраняется устаревший фокус на бакете после уменьшения capacity.
   Добавлены абсолютный масштаб и кнопка `1:1`: большие деревья можно рассмотреть
   даже на мобильном, независимо от автоматического масштаба обзора. Кнопка «−»
   корректно уменьшает диаграмму и при автоматическом масштабе ниже 15%.
8. Исправлен сброс позиции таймлайна после восстановления revision. Проверены
   конфликт команд без автоматического повтора мутации и воспроизведение offline.
9. E2E расширены на все initialCapacity и большие структуры. Добавлен режим
   production preview; CI настроен проверять собранный dist. Скриншоты документации
   обновляются только с UPDATE_SCREENSHOTS, обычные тесты не меняют рабочее дерево.
10. Обновлены README, описание API и **OpenAPI в YAML**, добавлены этот отчёт,
    воспроизводимый ресурсный сценарий и результаты измерений.

переполнения страницы. Большой сценарий содержит 97 узлов и split на два дерева.

## Размер trace и ресурсы

Измерения выполнялись локально: WSL2 / Ubuntu 26.04, Temurin 21.0.13,
Node 24.21.0, JVM `-Xms64m -Xmx256m`. Это проверка ограниченного учебного приложения,
а не SLA или прогноз производительности Selectel VDS.

| Операция | Полный JSON до оптимизации | Компактный JSON | Оценка gzip compact |
|---|---:|---:|---:|
| Resize распределённой таблицы, 97 элементов | 4 834 937 B | 838 377 B | ~11 kB |
| Split дерева, 97 элементов, обычные длинные строки | 37 357 623 B | 1 387 103 B | ~25 kB |
| Тот же split с максимальным экранированием строк | 129 203 118 B | 3 108 893 B | ~36 kB |

В обоих вариантах большого split сохранены **990 шагов** и **96 006 вхождений узлов
в снимки**. Компактный ответ хранит **830 различных версий** вместо повторяющихся
объектов. Сокращение JSON в наиболее объёмном измеренном случае — примерно 97,6%.
Gzip в таблице рассчитан offline (уровень 9); отдельно проверено реальное HTTP gzip
Tomcat. Размеры и задержки всех сценариев сохранены в артефактах.

Нагрузочный сценарий создаёт **19 сессий**, проверяет максимальные длины и 128 записей,
выполняет **четыре больших split одновременно**, затем **192 сценария удаления из
дерева** двумя пакетами при параллелизме 4. Ошибок запросов, OOM и расхождения
состояния не было. Для повторяющихся сценариев: p50 5.18 ms, p95 7.91 ms
в данном окружении; точные значения последнего прогона — в JSON ниже.

После двух пакетов с тем же числом сессий retained Java heap измеряется через
явный GC: **15.19 → 15.21 MiB**, изменение — 11 KiB. Устойчивого накопления trace
этот эксперимент не обнаружил. Пиковый RSS процесса — около **305 MiB**; heap и RSS
различаются из-за metaspace, JIT, стека и native-памяти. Ограничение heap 256 MiB
не означает ограничение всего процесса 256 MiB. Для будущего размещения разумно
начать с общего бюджета 512 MiB и повторить измерение уже на VDS.

После большого split и перемотки V8 used heap браузера после GC:
**~18,1 MiB desktop**, **~17,9 MiB mobile**. CDP также записывает embedder heap
(~24–25 MiB). Это не RSS всего Chromium. История ограничена 12 операциями;
полное тестирование 12 одновременно удерживаемых предельных trace не проводилось.

## Ограничения и следующий этап

- Только HashMap, String/Integer/TeachingKey/null; значения String/null;
  loadFactor 0.75. Лимиты записей и ID являются частью учебного MVP.
- Сессии одного процесса в памяти, TTL 30 минут, максимум 128. Перезапуск теряет
  сессии. Нет авторизации, БД, распределённого состояния и постоянной истории.
- Некоторые перекрашивания представлены снимком вращения/балансировки, а не
  отдельным событием на каждое присваивание. WORKING-состояния намеренно показывают
  временно незавершённую структуру; инварианты гарантируются для COMMITTED.
- Полный API-формат оставлен для совместимости и может быть очень большим.
  Для браузера используется compact; gzip сам по себе не уменьшает распакованный JSON.
- Проверены Chromium desktop/mobile. Firefox, Safari и физические телефоны не проверялись.
- Dockerfile/Compose подготовлены, но контейнерная сборка не запускалась: Docker
  Desktop не подключён к этой WSL-дистрибуции. JAR и production frontend проверены напрямую.
- Конфигурация GitHub Actions обновлена; удалённый запуск workflow в этой сессии
  не выполнялся. Доступные локальные эквивалентные проверки пройдены.
- Публичная публикация не выполнялась по указанию пользователя. Netlify frontend
  и существующий Selectel VDS backend остаются отдельным следующим этапом.

Локальные инструменты этой проверки установлены вне репозитория:
`~/.local/share/jcv-tools/jdk-21.0.13+9` и `~/.local/share/jcv-tools/browser-libs`.
Для повторения на этой машине установите JAVA_HOME на этот JDK и добавьте его `bin`
в PATH; Chromium потребует `LD_LIBRARY_PATH=~/.local/share/jcv-tools/browser-libs/usr/lib/x86_64-linux-gnu`
(используйте раскрытый `$HOME` при присваивании). Настройки shell пользователя не изменялись.
