# Архитектура и поведение коллекций

## Модули

```text
core/       Java 21
  engine/                 CollectionEngine<S>, CollectionDefinition<S>
  protocol/               Snapshot, Step<S>, Trace<S>, Scenario, CollectionType
  protocol/command/       совместимые Operation/Result и модели аргументов
  registry/               статический каталог фабрик и сценариев
  collections/hashmap/    движок, инструментированный алгоритм, ключи и снимки
  collections/arraylist/  движок, снимки, буферы и вхождения
backend/    Spring Boot
  web/                    маршруты, обработка ошибок, фильтр допуска
  dto/                    запросы, ответы и метаданные compact trace
  session/                SessionStore: блокировки, revision, TTL и квоты
  admission/              бюджеты запросов и определение адреса клиента
  error/                  ApiException
  trace/                  registry и кодировщики hashmap/arraylist
  observability/          счётчики и измерение записанного ответа
  config/                 CORS и ограничения JSON
frontend/   React + TypeScript
  app/                    композиция UI и статическая таблица представлений
  api/types/              общие envelopes и модели hashmap/arraylist
  api/trace/              диспетчер и декодеры compact-форматов
  session/                очередь запросов и восстановление сессии
  playback/               история trace и локальное воспроизведение
  features/hashmap/       диаграмма, layout, команды, детали узла и подписи
  features/arraylist/     диаграмма, команды и подписи
  components/             общие панели сценариев, метрик и событий
  presentation/           форматирование общей Operation
```

В core зависимости направлены от registry к реализациям коллекций, от реализаций
к engine/protocol. `CollectionDefinition<S>` связывает тип, класс снимка, фабрику
и сценарии. `CollectionRegistry.STANDARD` подключает HashMap и ArrayList.
`protocol/command` сохраняет текущий объединённый JSON-контракт аргументов и результатов;
преобразование учебного ключа принадлежит HashMapEngine.

Backend использует registry для создания движков и получения сценариев.
`CompactTraceRegistry.Registration<S>` связывает определения с кодировщиками,
проверяет тип каждого снимка и передаёт исходный trace. Кодировщики используют
DTO `SessionTrace<S>`; внутренние Frame/Refs и Encoder принадлежат своему формату.
Общие метрики читают счётчики session/admission, HTTP-фильтр управляет допуском
до завершения записи ответа. `Application` остаётся корнем Spring component scan.

Frontend выбирает controls, renderer и учебные метаданные через `collectionViews`.
Коллекционные presentation-функции готовят показатели и подписи; общие панели
отображают переданные данные. Декодеры восстанавливают ссылки готовых снимков Java.
Java unit-тесты следуют пакетам реализации, Spring integration-тесты проверяют
границы приложения, Vitest-тесты располагаются рядом с проверяемыми модулями.

Подключение коллекции: собственные engine/snapshot и сценарии → регистрация в core →
backend encoder → транспортные типы/декодер и frontend-представление → проверки JDK,
инвариантов, API и E2E. Список типов, команды и ограниченные метки ApiMetrics
обновляются вместе с контрактом новой коллекции.

Каждый запрос завершается на Java до воспроизведения. Перемотка выбирает готовый
snapshot. Следующая команда исполняется над **последним состоянием сервера**, даже
если пользователь смотрит ранний шаг или старую операцию. Во время запроса новые
команды отключены, но навигация по истории доступна. При потере ответа клиент
не повторяет мутацию, а запрашивает актуальное состояние.

## Просмотр диаграммы

На экранах до 680 px начальный масштаб — 100%: большая схема прокручивается
внутри ограниченного контейнера. На desktop начальный масштаб автоматически
вписывает схему по ширине. Кнопка «Вместить по ширине» доступна в обоих режимах;
reset возвращает начальный масштаб и начало прокрутки. Выбор бакета перемещает
вид к корню дерева или первому узлу списка, а «К выбранному узлу» возвращает
вид к выбранному узлу. Навигация не меняет trace и не вызывает API.

## Сценарии и тонкости JDK

| Сценарий | Реальные входные данные |
|---|---|
| Вставка | String `Java` → `Hello` |
| Коллизия | TeachingKey A/B/C, hashCode 42 |
| Обновление | `language`: `Java 17` → `Java 21` |
| Resize | `stay:1`, `move:17`, ещё 11 ключей: capacity 16 → 32; бакет 1 делится на 1/17 |
| Treeification | Конструктор с ёмкостью 64, девять ID K1…K9 с hashCode 42 |
| Почему нет дерева | Стандартный конструктор, девять тех же коллизий: capacity 16 → 32 |
| Поиск в дереве | После treeification — get(K7) |
| Удаление из дерева | После treeification — remove(K1)…remove(K8) |

`TREEIFY_THRESHOLD=8` — проверка счётчика при добавлении в уже существующую
цепочку, а не безусловное дерево на восьмой вставке. `UNTREEIFY_THRESHOLD=6`
применяется к половинам **split при resize**. Для обычного удаления JDK использует
проверку **формы** дерева (`root.right`, `root.left`, `root.left.left`), поэтому
универсального правила «удалили до шести — получили список» здесь нет.

`clear` сохраняет массив и закреплённые hashCode учебных ID; `reset` освобождает
таблицу и начинает новую коллекцию с параметрами, заданными при создании сессии.
Каждый сценарий задаёт свой конструктор и отражает это событием CONFIGURED:
64 для трёх сценариев дерева, стандартный конструктор для остальных.
Сценарии не наследуют initialCapacity сессии и не меняют её настройку RESET.
В режиме без выделенной таблицы threshold у конструктора с ёмкостью
содержит целевую ёмкость, а не обычный порог загрузки.

## Границы MVP

- HashMap: максимум 128 записей, 512 учебных ID на сессию. Значения — String/null.
- Load factor фиксирован 0.75; начальная ёмкость через API: 0 (default), 16, 32 или 64.
- Все шаги trace передаются целиком. Frontend использует компактную таблицу версий
  узлов; исходный полный формат API сохранён за явным `ALLOW_FULL_TRACE=true`.
  Без него `encoding=full` и запрос без encoding получают **403 FULL_TRACE_DISABLED**
  до исполнения команды, без изменения состояния/revision. Клиентам нужно явно
  указывать `encoding=compact`; подробности — в [API](API.md).
  Локальная история хранит 12 последних операций,
  не переживает обновление вкладки. Долгое воспроизведение не продлевает серверный TTL.
- Промежуточные WORKING-снимки могут временно нарушать итоговые инварианты, как реальный
  алгоритм. Ряд перекрашиваний объединён со снимком вращения или завершения балансировки;
  отдельное событие на каждое присваивание цвета не обещается.
- Algorithm — схема семантических этапов; это не построчная отладка исходника JVM.
- Авторизация, БД, распределённые сессии и коллекции помимо HashMap/ArrayList не добавлены.


## ArrayList: исполнение и наблюдение

Эталон — OpenJDK 21, тег `jdk-21.0.5+11`; [исходник ArrayList](https://github.com/openjdk/jdk21u/blob/jdk-21.0.5%2B11/src/java.base/share/classes/java/util/ArrayList.java).
`ArrayListEngine` хранит настоящий `Object[]` со String/Integer/null и параллельный
массив ID вхождений. ID не является адресом объекта. Новый set создаёт новое вхождение;
сдвиг/копирование сохраняет ID, одинаковые значения и null имеют независимые ID.
События записываются при исполнении операции; snapshots неизменяемы.

Отсутствующий initialCapacity — DEFAULT_EMPTY (capacity=0); explicit 0 —
EXPLICIT_EMPTY. Первые add выделяют 10 и 1 соответственно. Положительный конструктор
выделяет массив сразу. Рост соответствует безопасной ветви ArraysSupport.newLength:
`old + max(minimum-old, old >> 1)`. До аллокации проверяется вычисленная длина;
рост выше 256 отклоняется, даже если minimum ≤ 256. Огромные массивы/overflow JDK
не симулируются. Default ensureCapacity(10) ничего не выделяет; отрицательный
minCapacity — no-op. clear сохраняет массив; trim пустого выделенного массива
оставляет EXPLICIT_EMPTY; trim нетронутого default сохраняет DEFAULT_EMPTY.

При переносе snapshot содержит buffer и pendingBuffer с их ID, capacity и всеми
ячейками. ARRAY_ALLOCATED → ARRAY_COPY_STARTED → ARRAY_COPY_COMPLETED →
CAPACITY_GROWN/RESERVED/TRIMMED показывает выделение, эффект блочного копирования
ссылок и переключение elementData. Сдвиги выполняются реальным System.arraycopy;
WORKING может временно содержать дубликаты и ссылки за size. COMMITTED очищает хвост.
React только размещает готовые кадры; анимация отдельных ячеек иллюстрирует эффект
блочного копирования и не изображает Java-цикл.

Девять сценариев: first-add, explicit-zero, growth, insert-middle, remove-middle,
read-replace, nulls, capacity, linear-search. Каждый начинает с собственного reset,
последующий пользовательский RESET возвращает конструктор сессии. Все команды
сценария выполняются под одной сессионной блокировкой с одной новой revision.

Выбор коллекции атомарно заменяет структуру в существующем слоте через
POST /sessions/{id}/reset и очищает историю/выделение. UUID сохраняется, revision
увеличивается. Квота живых сессий не расходуется повторно. SessionConnection сериализует исполнение, смену структуры и восстановление,
сохраняя серверную revision даже из устаревшего для UI ответа. Счётчик поколения
защищает представление от запоздалых ответов; ещё не отправленные устаревшие
переключения пропускаются. Пока новая сессия создаётся, команды отключены.
Потерянная мутация никогда не повторяется автоматически; 409/ошибка сети вызывает GET.

`array-frames-v1` хранит каждую версию буфера и каждое вхождение один раз; кадры
ссылаются на эти пулы абсолютными индексами. Декодер разделяет неизменяемые объекты
между шагами. Пределы 128 элементов / 256 ячеек ограничивают также рабочие snapshots.
История содержит до 12 trace. В интерфейсе ячейки расположены сеткой с внутренней
вертикальной прокруткой; кнопки доступны клавиатурой, reduced motion отключает движение.


Замена engine не меняет алгоритмы коллекций. SessionStore проверяет IP-владельца,
TTL и revision под блокировкой сессии и только после успешной валидации конструктора
заменяет engine/collection. Освобождение через DELETE не требуется для переключений:
один слот переиспользуется на месте, отсутствует окно create-before-delete и нет
гонки позднего удаления с новой структурой. Новые вкладки, перезагрузки и неизвестный
результат create всё ещё ограничены общей квотой/TTL; постоянного хранилища нет.


## Физическая идентичность HashMap

Snapshot V2 разделяет логическую запись id и физический объект objectId. Все структурные
ссылки адресуют objectId. HashMapSnapshotAssembler сначала закрепляет реальные табличные
цепочки, затем inFlight и замыкание пяти ссылок; сборщик не меняет алгоритм. Каждый
объект имеет одно размещение, но рабочие рёбра могут пересекать области. Счётчики ID
принадлежат engine, не сбрасываются командой RESET; HTTP reset начинает новый engine.
Compact nodePool хранит версии физических объектов, nodeRefs — индексы версий.
Layout следует готовым ссылкам; выбор сохраняет logicalId/preferredObjectId для перемотки.
HashMap V1 не поддерживается. Для мутаций действует проверка совместимости до действия;
подробнее — API.md. Локальные split-сценарии добавляются в штатный ScenarioSidebar через динамический
импорт только при Vite serve и исключаются из любой build, включая нестандартный
NODE_ENV. Они используют существующую очередь сессии, Diagram, PlaybackPanel и
TraceInspector; отдельной страницы или backend-сценариев нет. Инспектор позволяет
выбирать физическое представление одной записи при наличии нескольких объектов.
