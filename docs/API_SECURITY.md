# Ограничения публичного API

Защита работает в одном Java-процессе, без Redis/БД. Она дополняет ограничения
Tomcat и systemd; CORS не заменяет её. Приложение опубликовано; этот документ описывает
реализованные ограничения и контракт конфигурации, а не состояние живого сервера.

## Правила

- `POST /api/v1/sessions`: отдельный счётчик создания сессий на IP за окно.
- Замена `/sessions/{id}/reset` использует рабочий бюджет и не создаёт новый слот.
- Остальные POST под `/api/` и `GET /api/v1/sessions/{id}`: общий счётчик работы
  на IP. GET-снимки учитываются, поскольку тоже сериализуют состояние коллекции.
  Неуспешные запросы после допуска также расходуют лимит; отклонённые до допуска — нет.
- Для всей этой работы действует общий и отдельный на IP предел одновременных
  запросов. Слот удерживается до конца записи JSON, включая compact-кодирование.
  Освобождается и при ошибке/отключении клиента. При занятости слот не ожидается.
  Ограниченная очередь соединений Tomcat остаётся отдельным механизмом.
- IP не может иметь больше разрешённого числа **живых** сессий, даже создавая их
  медленно в разных окнах. TTL и глобальный предел SessionStore сохраняются.
  Очистка TTL освобождает квоту; clear/движковый reset её не освобождают.
  Сессионный `/reset` заменяет структуру в том же слоте, не занимая дополнительную квоту.
- `/health`, список сценариев и OPTIONS не занимают рабочие слоты. Браузерная
  перемотка вообще не обращается к API.
- Счётчики ограничены числом клиентов; бездействующие записи очищаются раз в окно.
  При заполнении таблицы новые IP отклоняются до следующей очистки, активные
  записи не вытесняются с обнулением счётчика.

Все отказы ограничения — **429**, JSON `{schemaVersion, code, message}` и
`Retry-After` в целых секундах (минимум 1). Коды: `RATE_LIMITED` (частота),
`WORK_LIMIT` (заняты слоты), `CLIENT_TRACKING_LIMIT` (таблица счётчиков),
`CLIENT_SESSION_LIMIT` (живые сессии IP). Новый запрос ещё не исполнялся: HashMap
и revision не меняются. Общий заполненный пул по-прежнему даёт **503 SESSION_LIMIT**.
Приоритет проверки ограничений — перед MVC и проверкой encoding/revision;
например, перегруженный full-запрос может получить 429 вместо 403.

После 429 можно повторить явно выбранную пользователем команду с той же revision,
если её не изменила другая команда. Автоматический повтор мутаций не добавлен.
При потере ответа/сетевой ошибке результат неизвестен: сначала получите сессию.
Для разрешённого origin JSON ошибки 429 доступен через CORS; wildcard не используется.

## Параметры

| Environment | По умолчанию | Значение |
|---|---:|---|
| `RATE_WINDOW_SECONDS` | 60 | Длительность независимого окна клиента |
| `SESSION_CREATE_RATE_LIMIT` | 30 | Создания за окно на IP |
| `WORK_RATE_LIMIT` | 600 | Команды, сценарии и чтения снимков за окно на IP |
| `MAX_CONCURRENT_WORK` | 2 | Одновременно во всём процессе |
| `MAX_CONCURRENT_WORK_PER_CLIENT` | 1 | Одновременно на IP |
| `MAX_TRACKED_CLIENTS` | 4096 | Максимум записей счётчиков |
| `MAX_SESSIONS_PER_CLIENT` | 0 | 0 = `min(32, max(1, MAX_SESSIONS / 4))`; положительное число — явный предел |
| `TRUSTED_PROXIES` | пусто | Точные IP доверенных прямых proxy, через запятую; без DNS/CIDR |

Положительные лимиты обязательны; TTL должен быть от 1 до 2147483647 секунд.
По умолчанию MAX_SESSIONS=128 даёт 32 сессии/IP. При существующем MAX_SESSIONS=32
автоматический предел составляет **8**, даже если новая переменная не добавлена
в env-файл. Env-пример описывает настройки приложения, а не действующую production-политику. Для локальной диагностики можно явно повысить лимиты; не
используйте отключение защиты или произвольные proxy-заголовки для production.

## Адрес клиента за Caddy

По умолчанию используется только адрес TCP-пира. `X-Forwarded-For`, `Forwarded`
и чужой `X-JCV-Client-IP` не меняют идентичность клиента.
`server.forward-headers-strategy=none` отключает предварительное переписывание
адреса контейнером Spring/Tomcat.

При размещении за reverse proxy настройте обе стороны согласованно:

1. Proxy перезаписывает `X-JCV-Client-IP` адресом непосредственного клиента.
   Универсальный пример для локального backend (не production-конфигурация):

   ```caddyfile
   @diagnostics path /actuator /actuator/*
   respond @diagnostics 404
   reverse_proxy 127.0.0.1:8080 {
       header_up X-JCV-Client-IP {remote_host}
   }
   ```
2. `TRUSTED_PROXIES` содержит только точные адреса доверенных proxy.
   Backend должен быть доступен только proxy, без публичного обходного порта.
3. Проверяйте, что поддельный входящий заголовок не меняет квоту клиента.
   Применение настроек и проверка живого сервера — отдельная операция владельца.

Доверие даётся только точному непосредственному proxy. Принимается ровно одно
значение custom-заголовка с корректным числовым IPv4/IPv6; DNS-имена, цепочки,
дубликаты и зоны IPv6 не принимаются. IPv4-mapped IPv6 нормализуется в IPv4.
Некорректный/отсутствующий заголовок консервативно объединяет клиентов под адресом
proxy. Не включайте доверие loopback за публично доступным произвольным прокси.
Без согласованной настройки все запросы через Caddy разделят одну квоту; это
безопасный отказ, но снижает доступность для разных посетителей.

Ограничения IP объединяют пользователей за NAT. Распределённые атаки, массовая
смена IPv6-адресов и защита сетевого канала требуют мер провайдера/edge; это не
аутентификация. UUID сессий и существующая семантика доступа не меняются.

## Проверка ресурсов

Тесты покрывают окна/TTL, занятость слотов, освобождение при ошибке записи ответа,
ограниченность счётчиков, spoofed headers, URL aliases MVC и неизменность revision.
Локальная проба использует отдельный процесс на порту 18090, heap 256 MiB и один
видимый процессор; HTTP-отказы считаются ожидаемым результатом защиты.
В [артефакте прогона](verification/api-limits-local.json) окно ускорено до 2 секунд:
6 созданий допускаются, после нового окна живой предел остаётся 8; поддельные
proxy-заголовки не создают новые квоты. Из 8 одновременных предельных split одна
операция прошла (990 шагов, 3,11 МБ compact), семь получили 429 без мутации.
Далее 96 запросов дали 12 успешных сценариев, 8 ожидаемых revision conflict,
69 отказов занятости и 7 отказов частоты. Все 16 запросов health прошли,
максимальная задержка 60,84 мс. За 3,51 с измерено 2,46 с CPU процесса;
пиковый RSS 175,1 MiB. `ActiveProcessorCount=1` не является OS CPU quota.
Это короткая локальная проба, не SLA и не доказательство отсутствия утечек.
Реальная нагрузочная проверка CPU/RAM **на VDS не выполнялась**: она требует
отдельного разрешения владельца и не входит в локальное подтверждение характеристик.


## Разбор ошибок сессий для 0.3.1

[Результаты расследования и границы подтверждения](verification/session-lifecycle.md).
Не повышайте лимиты для компенсации повторных созданий: переключение UI теперь
переиспользует слот. Новые вкладки и пользователи за NAT по-прежнему делят IP-квоты;
лимиты частоты являются отдельной защитой и могут законно возвращать RATE_LIMITED.
Наличие правильного proxy-файла не доказывает, что работающий Caddy загрузил его:
при диагностике проверяйте фактический маршрут и перезапись пользовательского
custom-заголовка, не разрешая доверие произвольным адресам/цепочкам.
