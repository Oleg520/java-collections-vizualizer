# Java Collections Visualizer — архитектурное видение

> **Статус:** согласованное направление развития, **не** задание на немедленную реализацию.  
> **Назначение:** долговременный ориентир для архитектурных решений, ревью и планирования развития проекта.  
> **Приоритет:** сначала закончить и проверить текущий функционал; архитектурные изменения проводить поэтапно и с тестами.  
> **Связанные документы:** `SPEC.md` (если присутствует), `docs/ARCHITECTURE.md`, `docs/API.md`, `docs/TESTING.md`.

## 1. Замысел продукта

Java Collections Visualizer — интерактивная образовательная лаборатория, которая **показывает внутреннюю работу основных реализаций коллекций Java**, а не только результат вызова публичных методов.

Главная аудитория — изучающие Java разработчики, в том числе готовящиеся к техническим собеседованиям. Пользователь должен видеть причинно-следственную цепочку: *команда → этапы алгоритма → изменения внутренней структуры → итоговое состояние*.

**Ближайший фокус** — базовые коллекции из `java.util` и наиболее востребованные на собеседованиях механизмы. Долгосрочно платформа может охватить и другие механизмы Java; это **не** расширяет текущий MVP.

### Порядок развития (ориентир, не обязательный roadmap)

1. **Базовые коллекции:** HashMap, ArrayList, LinkedList, HashSet; далее — TreeMap/TreeSet, ArrayDeque, PriorityQueue и другие уместные реализации.
2. **Потокобезопасные структуры и примитивы:** ConcurrentHashMap, BlockingQueue, AtomicInteger, CAS, синхронизация, блокировки — только после базовых коллекций.
3. **Более общие механизмы Java:** при обоснованном спросе, отдельными модулями и с отдельными моделями визуализации.

Не требуется реализовывать все коллекции сразу. Приоритет и глубина каждой новой реализации определяются образовательной пользой и сложностью.

## 2. Что именно мы моделируем

**Решение:** воспроизводить фундаментальные механизмы конкретной реализации на основе выбранной версии OpenJDK (базовый ориентир — Java 21), с инструментированными точками наблюдения.

- **Это не непосредственное исполнение `java.util.HashMap`, `java.util.ArrayList` и т. п.** Внутренние поля стандартных объектов не читаются через reflection ради визуализации; используются собственные инструментированные реализации/модели, воспроизводящие существенные алгоритмы.
- **Не нужно гоняться за каждой новой версией JDK.** Мы демонстрируем устойчивые принципы, а не обещаем побайтовую идентичность с произвольной версией JVM.
- **Точность важнее зрелищности.** Упрощения допустимы для образовательных целей, но должны быть обозначены; нельзя показывать упрощённый механизм как фактический алгоритм OpenJDK.
- **Контракт Java API и детали реализации — не одно и то же.** Обратная совместимость API не гарантирует неизменность внутренних структур.
- **Лицензии и происхождение исходников обязательны.** Если код адаптирован из OpenJDK, сохранять необходимые copyright/license notices, обозначать версию/источник и изменения.

Примеры механизмов:

| Коллекция | Что показываем в первую очередь |
| --- | --- |
| HashMap | hash/spread, индекс бакета, коллизии, цепочки, resize/split, treeification, красно-чёрное дерево |
| ArrayList | внутренний массив, size/capacity, рост, копирование ссылок, сдвиги, доступ по индексу |
| LinkedList | `first`/`last`, `prev`/`next`, обход, вставка и удаление узлов |
| HashSet | уникальность элементов и использование HashMap как механизма хранения |
| TreeMap / TreeSet | порядок, сравнение ключей, дерево поиска, балансировка |
| ArrayDeque | кольцевой буфер, head/tail, расширение |
| PriorityQueue | бинарная куча, sift-up/sift-down, операции с приоритетами |

Для структур-обёрток, например HashSet поверх HashMap, **предпочитать переиспользование существующего механизма**, сохраняя отдельное учебное представление, вместо независимого дублирования алгоритма.

## 3. Главные архитектурные принципы

1. **Java — источник истины.** Именно Java-движок исполняет операцию и определяет состояние структуры; frontend не повторяет алгоритмы коллекций.
2. **События имеют смысл.** Движок публикует семантические шаги (вычисление hash, выбор бакета, перенос элементов, связь узлов, балансировка и т. д.), а не абстрактные команды «перекрасить пиксель».
3. **Воспроизводимое состояние.** Для каждого шага доступен достаточный снимок (или семантически эквивалентное, восстанавливаемое представление), чтобы реализовать паузу, перемотку и пошаговый просмотр **без повторного исполнения команды**.
4. **Коллекции изолированы.** Их собственные операции, внутренние структуры, события и модели состояний не смешиваются. Добавление нового типа не требует переписывать логику старого.
5. **Общее ядро — небольшое.** Общими делаем только реально разделяемые контракты; не вводим универсальные абстракции ради абстракций.
6. **Расширение через регистрацию.** Общие компоненты узнают о новой коллекции через registry/provider, а не через нарастающие `if`/`switch` по всем известным типам.
7. **Разделение обязанностей.** Domain/core не зависит от Spring, HTTP, JSON, React и SVG. Backend управляет API/сессиями/кодированием; frontend отвечает за представление и управление воспроизведением.
8. **Проверяемость.** Для каждой коллекции нужны тесты поведения против JDK, отдельные проверки структурных инвариантов и end-to-end проверка пользовательских сценариев.
9. **Контролируемая сложность.** Все изменения должны иметь измеримую пользу для поддержки следующей коллекции; не строим сразу фреймворк «для всех механизмов Java».

## 4. Целевые границы модулей

Сохраняем **единый монорепозиторий** и разделение по модулям:

```text
java-collections-vizualizer/
├── core/         # чистые Java-алгоритмы, двигатели, снимки и семантические события
├── backend/      # REST, сессии, лимиты, конфигурация, сериализация/compact trace
├── frontend/     # UI, визуальные renderer'ы, управление trace и анимации
├── docs/         # архитектура, контракты, тестирование, решения
└── deploy/       # инфраструктура и доставка (если предусмотрено репозиторием)
```

### Предлагаемая структура Java core

```text
dev.collectionsviz
├── engine/
│   ├── CollectionEngine.java
│   ├── CollectionProvider.java      # регистрация/создание реализаций
│   └── EngineConfig.java            # общая форма параметров создания, если нужна
├── protocol/
│   ├── Operation.java               # общий контракт команды / типизированный envelope
│   ├── Step.java
│   ├── Trace.java
│   ├── Snapshot.java
│   └── ...                          # только действительно общие модели
└── collections/
    ├── hashmap/
    │   ├── HashMapEngine.java
    │   ├── InstrumentedHashMap.java
    │   ├── HashMapSnapshot.java
    │   ├── HashMapOperation.java
    │   └── ...
    ├── arraylist/
    │   ├── ArrayListEngine.java
    │   ├── ArrayListSnapshot.java
    │   ├── ArrayListOperation.java
    │   └── ...
    ├── linkedlist/                 # когда появится реализация
    └── ...
```

Это **иллюстрация границ ответственности**, а не требование создавать все перечисленные классы и интерфейсы немедленно. Конкретные имена и степень дробления могут уточняться при рефакторинге.

**Текущая структура протокола:** общие контракты расположены в `protocol/`, снимки — в пакетах коллекций. `protocol/command` сохраняет совместимый объединённый формат команд и результатов. Дальнейшая типизация операций рассматривается при расширении контракта.

## 5. Collection Registry — ключевое решение

**Цель:** добавление очередной коллекции не должно требовать новых условий по типу коллекции в `ApiController`, `SessionStore`, общем механизме сценариев и кодирования trace.

Предлагается модель **регистрации collection provider/module**. У каждого поддерживаемого типа есть стабильный идентификатор, фабрика движка, описание доступных операций и сценариев. Транспортный кодировщик и frontend-renderer подключаются на своих уровнях.

Схема ответственности:

```text
                 [ Collection Registry / каталог типов ]
                                |
            +-------------------+-------------------+
            |                   |                   |
      HashMap provider    ArrayList provider   LinkedList provider
            |                   |                   |
      HashMapEngine        ArrayListEngine      LinkedListEngine
            |                   |                   |
      HashMapSnapshot      ArrayListSnapshot    LinkedListSnapshot

backend: engine registry + registry кодировщиков trace (HTTP/JSON)
frontend: registry визуализаторов и панелей действий (UI)
```

**Пример идеи, не утверждённый API и не инструкция копировать буквально:**

```java
public interface CollectionProvider<S extends Snapshot> {
    CollectionId id();
    CollectionEngine<S> create(CollectionConfig config);
    List<OperationDescriptor> operations();
    List<ScenarioDescriptor> scenarios();
}
```

- `CollectionProvider`/фабрика относится к доменному уровню; он **не знает** о Spring, JSON и React.
- `TraceEncoder` для компактного API — ответственность backend, регистрируемая по типу коллекции. Не помещать JSON-кодировщик в `core`.
- Renderer, layout и интерфейс ввода команд — ответственность frontend, со своим registry по идентификатору коллекции.
- Необязательно делать runtime plugin loading, SPI/JAR-плагины или динамическую загрузку кода. **Обычной статической регистрации при старте приложения достаточно.**
- Registry должен проверять дублирующиеся идентификаторы и понятным образом сообщать о неподдерживаемом типе.
- Типизация должна оставаться безопасной: по возможности избегать бесконтрольных приведений `Object` и ветвления по строковым значениям типов во многих местах.

### Добавление новой коллекции — целевой процесс

1. Реализовать её движок и инструментированный алгоритм в отдельном пакете.
2. Определить операции, снимки и семантические события именно этой коллекции.
3. Зарегистрировать provider/factory и учебные сценарии.
4. Добавить кодировщик trace в backend и renderer/controls в frontend.
5. Добавить unit/invariant/differential и E2E-тесты; обновить документацию.
6. **Не менять** внутренний алгоритм другой коллекции, чтобы новая появилась в UI/API.

## 6. Протокол событий и снимков

Желаемый общий принцип:

```text
Operation
   → CollectionEngine.execute(...)
   → Trace { before, steps: [event + snapshot], committed, result }
   → Backend API / компактное представление
   → Frontend playback / renderer
```

Базовые обобщённые понятия: `Operation`, `Trace<S>`, `Step<S>`, `Snapshot`, `Result`/результат операции. Но **конкретное содержимое** операций, снимков и полей событий принадлежит отдельной коллекции.

- Не заставлять LinkedList иметь «бакеты», а HashMap — «ячейки массива ArrayList» ради общего DTO.
- Не превращать универсальную `Operation` в бесконечный набор опциональных полей. При расширении оценить типизированные операции/дискриминируемые варианты с сохранением удобного REST-контракта.
- Стабильные идентификаторы узлов/элементов помогают отображать реальные перемещения и сохранять непрерывность анимации.
- События должны различать фактический механизм и его учебную иллюстрацию; не выдавать анимацию `System.arraycopy` за Java-цикл поэлементного копирования.
- Можно применять компактное кодирование и дедупликацию snapshots, но **смысл и порядок шагов не должны теряться**. Оптимизация транспорта не должна протекать в реализацию алгоритма.
- При изменении внешнего протокола учитывать совместимость backend/frontend и версионирование API/trace.

## 7. Backend и frontend без жёстких зависимостей

### Backend

В `backend` остаются создание/восстановление сессий, revision, TTL, лимиты, безопасность, маршруты REST и формат выдачи. Его общие компоненты должны работать с движком через контракт и registry.

**Текущая реализация:** статические `CollectionRegistry` в core и `CompactTraceRegistry`
в backend связывают фабрики, сценарии и кодировщики HashMap/ArrayList. Подробности —
в [архитектуре](ARCHITECTURE.md).

Целевой результат: API получает идентификатор коллекции → находит provider → создаёт engine → применяет операцию → выбирает соответствующий encoder, не расширяя центральный контроллер очередным `switch`.

### Frontend

Предпочитаем разделять:

- общий каркас: выбор коллекции, сессия, очередь запросов, история trace, playback, управление скоростью;
- описание конкретной коллекции: доступные операции, форма ввода, подсказки и примеры;
- визуализатор конкретной структуры: layout, SVG/DOM элементы, выделение и анимация.

В перспективе UI выбирает модуль отображения через registry, а не через постоянно разрастающийся `App.tsx`. **Никакого дублирования Java-алгоритмов на TypeScript.**

## 8. Качество и критерии готовности архитектурного улучшения

Рефакторинг полезен, если после него выполняются следующие условия:

- **Действующий функционал HashMap и ArrayList сохранён.** Никаких регрессий в событиях, сценариях, API, анимациях и пользовательском опыте.
- `core` компилируется и тестируется отдельно от Spring и frontend.
- Тесты сравнивают публичное поведение инструментированной реализации с JDK и проверяют важные внутренние инварианты.
- Общие API/сессии не зависят от конкретных классов HashMap/ArrayList, кроме регистрации адаптеров.
- Добавление LinkedList можно объяснить как «новый модуль + регистрации + renderer + тесты», а не «изменить десять общих классов».
- Нет лишней инфраструктуры: plugin marketplace, reflection-based discovery, отдельные микросервисы и тяжёлые DI-иерархии **не требуются**.
- API-контракт и формат trace либо совместимы с текущим frontend, либо изменения мигрируются одновременно и подтверждаются E2E-тестами.

## 9. Последовательность внедрения

**Сейчас:** не начинать архитектурный рефакторинг только ради этого документа. Сначала завершить текущие задачи, проверить сборку, тесты, UX и стабильность.

**Затем, отдельным запланированным изменением:**

1. Провести точечный аудит зависимостей и определить, какие сущности действительно общие.
2. Разделить пакеты `core` и разнести протоколы конкретных коллекций без изменения поведения.
3. Ввести минимальный registry/factory для движков и сценариев; убрать прямой выбор конкретной коллекции из общих API-компонентов.
4. Вынести регистрацию compact-encoders на уровень backend и renderer/controls — на уровень frontend.
5. Подтвердить отсутствие регрессий, обновить архитектурную документацию и только после этого добавлять следующую коллекцию.

Делить работу на небольшие PR, не объединять масштабный рефакторинг с реализацией новой структуры данных. Если появятся более простые решения, предпочтительна **простая архитектура с теми же границами ответственности**.

## 10. Границы решения / что пока не решаем

- Не реализуем `java.util.concurrent`, CAS и другие JVM-механизмы в текущем этапе; сохраняем возможность добавить отдельный предметный модуль позднее.
- Не требуем моделирования произвольных версий JDK и переключения версий на лету.
- Не определяем заранее все будущие коллекции, события или варианты UI.
- Не переходим на микросервисы и не разбиваем монорепозиторий ради расширяемости.
- Не обещаем точной имитации всех внутренних оптимизаций OpenJDK; любые дидактические упрощения документируем.
- Не смешиваем архитектурное видение с задачами публикации на Netlify/Selectel — деплой имеет собственный план и жизненный цикл.

---

**Суть архитектурного решения:** Java Collections Visualizer должен эволюционировать от визуализации отдельных коллекций к **расширяемой образовательной платформе механизмов Java**, сохраняя Java как источник истины, независимые реализации коллекций и маленькое общее ядро. Registry — способ подключения новых реализаций **без разрастания центральной логики**, а не самоцель.
