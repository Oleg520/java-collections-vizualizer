Создай работающее веб-приложение по этой спецификации. Если репозиторий пустой, самостоятельно инициализируй проект. Если код уже существует, сначала изучи его и сохраняй совместимость с полезными наработками.

Принимай технические решения самостоятельно в рамках выбранного стека и архитектурных принципов ниже. Не ограничивай себя искусственно количеством классов, библиотек, файлов или этапов: важнее корректная работа, понятная кодовая база и удобный интерфейс. Не превращай проект в набор заглушек или статичных демонстраций.

Реализуй **полноценный вертикальный срез**: Java-движок → API → последовательность событий и состояний → интерактивная анимация в браузере. По возможности запускай тесты, сборку и локальную проверку; в конце опиши реализованное, принятые решения, команды запуска и известные ограничения. ## 1. Идея и цель

Создать интерактивный учебный инструмент для изучения **внутреннего устройства коллекций Java**. Пользователь выбирает коллекцию, вызывает её операции и наблюдает не только итоговое содержимое, но и **реальные шаги алгоритма**: вычисления, переходы, создание узлов, изменения связей, реорганизацию структуры.

Это не универсальный редактор диаграмм и не визуализатор псевдокода: логика выполняется **на Java**, а браузер визуализирует результат выполнения Java-движка.

В MVP реализовать только **`HashMap`**. Архитектуру предусмотреть для добавления `ArrayList`, `LinkedList`, `HashSet`, `LinkedHashMap`, `TreeMap` и других структур в будущем, но **не реализовывать их сейчас**.

### Ключевой пользовательский сценарий

1. Пользователь открывает сайт и выбирает `HashMap`.
2. Видит таблицу бакетов, размер, фактическую ёмкость, порог расширения, `loadFactor`, историю событий и доступные операции.
3. Вводит ключ и значение, вызывает `put` (или `get` / `remove`).
4. Java-движок исполняет операцию и формирует упорядоченный **trace** из семантических событий и снимков внутреннего состояния.
5. Фронтенд воспроизводит trace шаг за шагом, плавно анимируя изменения; пользователь может поставить на паузу, перейти назад/вперёд и изучить объяснения.
6. При коллизии видно цепочку в одном бакете, при `resize` — распределение узлов по новым бакетам, при `treeify` — красно-чёрное дерево.

## 2. Технологический стек

**Обязательная основа:**

- **Java 21** — вся логика коллекций и генерация событий.
- **Spring Boot** — backend и HTTP API.
- **React + TypeScript** — frontend.
- **Vite** — frontend tooling/build.
- **Tailwind CSS** — оформление интерфейса.

Библиотеки анимации, state management, графов/деревьев, сборщик Java (Gradle/Maven) и тестовые инструменты выбери самостоятельно. React Spring, Motion и SVG — допустимые варианты, но не обязательная конкретная реализация.

Предпочтителен **монорепозиторий** с чётко выделенными областями Java-ядра, Spring Boot API и frontend. Ядро алгоритмов должно быть **независимым от Spring и UI**, чтобы его можно было отдельно тестировать и потенциально переиспользовать.

**На этапе MVP** хранение пользовательских сессий в памяти допустимо. Постоянная БД, авторизация и сложная инфраструктура не являются целью первой версии; добавляй их только при наличии конкретной необходимости.

## 3. Архитектурные инварианты

### 3.1 Java — единственный источник истины

- Java-модель владеет состоянием структуры данных, исполняет операции и генерирует семантические события.
- React **не реализует алгоритм `HashMap` повторно**: не вычисляет за Java хеши, не решает, когда расширить таблицу, не строит собственную логику treeification.
- React отвечает за представление, размещение узлов, управление временем воспроизведения и анимацию переходов между состояниями.
- События генерируются из **реального потока исполнения инструментированной Java-модели**, а не реконструируются по разнице финальных состояний.

### 3.2 Визуализация независима от алгоритма

- Отдели **команды** (`put`, `get`, `remove`, `clear`/`reset`), **семантические события**, **снимки состояния** и **рендеринг**.
- Событие описывает *что произошло и почему*, а не *где нарисовать квадрат*. Например, `BUCKET_SELECTED`, а не `MOVE_RECTANGLE_TO_X_240`.
- Координаты, продолжительность анимаций и CSS-параметры не должны попадать в Java-алгоритм.
- Новая коллекция может иметь свою схему состояния и специализированный renderer, но должна переиспользовать общую инфраструктуру команд, trace и управления воспроизведением.
- Не обязательно создавать абстракции под все будущие коллекции заранее; достаточно честных точек расширения без жёсткой привязки всей системы к `HashMap`.

### 3.3 Воспроизведение и консистентность

- Каждая операция возвращает **детерминированно упорядоченную последовательность шагов**.
- Для каждого визуализируемого шага доступен снимок состояния (или функционально эквивалентный механизм, позволяющий однозначно восстановить состояние).
- Переходы **назад**, **вперёд**, **pause/play**, **restart текущей операции**, смена скорости не должны заново выполнять или менять уже завершённую Java-операцию.
- У узлов должны быть стабильные идентификаторы в пределах их жизненного цикла, чтобы фронтенд мог показывать именно перемещение/изменение, а не случайную замену элементов.
- Явно различай **рабочее/промежуточное состояние шага** и **зафиксированное состояние коллекции после операции**.

## 4. Корректность HashMap (OpenJDK 21)

Визуализируемая `HashMap` должна иметь собственную **инструментированную Java-реализацию**, совместимую с изучаемой логикой OpenJDK 21. Не пытайся извлекать внутренние бакеты `java.util.HashMap` через рефлексию. Допускается использование стандартной `HashMap` **в тестах как эталона наблюдаемого поведения**.

Реализовать и объяснять:

- `put(key, value)`, `get(key)`, `remove(key)`; возможность очистить коллекцию / начать заново.
- Вычисление `key.hashCode()` и его преобразование в hash, включая правило `h ^ (h >>> 16)` и случай `null`.
- Вычисление индекса бакета: `(capacity - 1) & hash`.
- Ленивое создание таблицы при первой вставке (не показывать выделенный массив на 16 элементов до фактической инициализации, если он ещё не выделен).
- Добавление в пустой бакет, поиск по цепочке, сравнение hash и ключей через `equals`, обновление значения существующего ключа.
- Коллизии и связные списки внутри бакетов.
- `size`, `capacity`, `loadFactor`, `threshold`; обычную начальную ёмкость **16**, `loadFactor = 0.75`, рост таблицы и перераспределение узлов при `resize`.
- Объяснение реального механизма split при удвоении ёмкости (`hash & oldCapacity`): запись остаётся в прежнем индексе либо переходит в `oldIndex + oldCapacity`.
- Преобразование длинной цепочки в **красно-чёрное дерево** при условиях OpenJDK 21; отображение цвета, связей `left/right/parent`, а также состояния бакета.
- Балансировку дерева при вставке: по возможности отдельные шаги вращений и перекрашиваний там, где они реально происходят.
- Удаление из списка/дерева; обратное преобразование tree → list, **когда оно действительно происходит по правилам JDK**. Не объяснять его неверным универсальным правилом «при 6 узлах» для любых удалений.
- Особенности `null`-ключа и `null`-значения, если доступны в пользовательском вводе.

**Опорные константы OpenJDK 21:** `TREEIFY_THRESHOLD = 8`, `UNTREEIFY_THRESHOLD = 6`, `MIN_TREEIFY_CAPACITY = 64`. Обязательно учитывать, что при недостаточной ёмкости попытка treeification вызывает `resize`. Проверить точную off-by-one семантику перехода на дерево по исходнику: не трактовать `TREEIFY_THRESHOLD` как безусловное преобразование ровно на восьмой вставке.

Референсный код: [OpenJDK 21 HashMap.java](https://github.com/openjdk/jdk21u/blob/master/src/java.base/share/classes/java/util/HashMap.java). Используй его как источник поведения; при заимствовании исходного кода соблюдай лицензионные требования. В README честно называй проект *учебной инструментированной реализацией, ориентированной на OpenJDK 21*, а не утверждай, что это прямое наблюдение приватных объектов JVM.

### 4.1 Ключи для управляемых коллизий

Демонстрации невозможно надёжно проводить, полагаясь только на случайно подобранные строки. Дай пользователю простой способ **намеренно создавать разные ключи с одинаковым `hashCode()`**.

Подход: специальный Java-тип учебного ключа с отображаемым идентификатором и заданным `hashCode`, корректными `equals`/`hashCode`, стабильными параметрами на протяжении сессии. При необходимости реализуй `Comparable`, чтобы дерево имело объяснимый и воспроизводимый порядок для учебных сценариев.

Важно:

- Разные ключи с одним хеш-кодом должны оставаться разными ключами, если `equals` возвращает `false`.
- Повторная вставка того же ключа обновляет значение, не увеличивая `size`.
- Не допускать незаметной смены `hashCode` уже существующего логического ключа.
- Должен быть режим обычных интуитивных ключей (например, строки/целые) либо понятное объяснение учебного режима. Явно показывать, какой именно тип ключа сейчас используется.

## 5. События, снимки состояния и API

Предоставь версионируемый и документированный JSON-контракт, понятный независимо от React.

**Пример желаемого смысла ответа (иллюстрация, не жёсткая JSON-схема):**

```json
{
  "operation": { "type": "PUT", "key": "A", "value": "Hello" },
  "result": { "previousValue": null },
  "steps": [
    {
      "index": 0,
      "event": "HASH_CALCULATED",
      "message": "Вычислен hash ключа A",
      "details": { "rawHashCode": 42, "spreadHash": 42 },
      "snapshot": { "capacity": 0, "size": 0, "buckets": [] }
    },
    {
      "index": 1,
      "event": "TABLE_INITIALIZED",
      "message": "Выделена таблица на 16 бакетов",
      "details": { "capacity": 16, "threshold": 12 },
      "snapshot": { "capacity": 16, "size": 0, "buckets": [] }
    },
    {
      "index": 2,
      "event": "BUCKET_SELECTED",
      "message": "(16 - 1) & 42 = 10",
      "details": { "bucketIndex": 10 },
      "snapshot": { "capacity": 16, "size": 0, "buckets": [] }
    }
  ]
}
```

В реальном контракте snapshot должен содержать **всё необходимое** для корректной визуализации: размеры и пороги, бакеты, элементы, стабильные ID, хеши, цепочки и структуру дерева с цветами/связями. Пример выше намеренно сокращён и не задаёт точную форму.

Предусмотри события по смыслу: начало/конец операции, вычисление хеша, выбор бакета, сравнение ключей, вставка/замена/удаление узла, коллизия, начало/конец `resize`, перемещение/split, начало/конец treeification, изменения дерева, результат `get`/`remove`. **Точный набор событий определяет реализация**, но пользователь должен видеть причинно-следственную цепочку, а не один кадр «до» и один «после».

В каждом шаге желательно поддержать:

- короткое понятное объяснение на русском языке с Java-терминами;
- технические детали (формула, сравниваемые ключи, индекс, порог, причина решения);
- подсветку задействованных бакетов/узлов;
- ссылку на семантический этап алгоритма, позволяющую в будущем подсвечивать соответствующий фрагмент Java/pseudocode.

API может работать по **HTTP/REST**: создать учебную сессию, получить её текущее состояние, выполнить операцию и получить trace, сбросить сессию/коллекцию. Конкретные URL и DTO спроектируй самостоятельно. Для MVP передача trace целиком предпочтительнее обязательных WebSocket/SSE: воспроизведение и пауза должны работать без постоянного соединения.

Состояния разных пользователей/вкладок не должны смешиваться. Если используются серверные in-memory-сессии, обеспечь изоляцию, корректную обработку конфликтующих команд и разумную очистку неактивных сессий.

## 6. UX/UI и анимации

Интерфейс должен выглядеть как **качественный интерактивный инструмент разработчика**, а не как простая таблица со строками логов.

### Главный экран

- Название проекта и выбор коллекции (в MVP доступна `HashMap`; расширение предусмотрено).
- Панель операций: ввод ключа и значения, `put`, `get`, `remove`, reset; безопасная валидация.
- Основная визуальная область: массив бакетов с индексами; внутри — отдельные узлы, стрелки и, где нужно, красно-чёрное дерево.
- Показатели состояния: `size`, `capacity`, `threshold`, `loadFactor`, результат последней операции.
- Панель **Algorithm / Events**: последовательность шагов, текущий шаг, объяснение, технические подробности.
- Управление воспроизведением: play/pause, шаг назад/вперёд, переход к началу/концу и скорость анимации.

### Требования к визуализации

- Плавно анимировать появление, удаление, перемещение и перестройку связей; выделять изменившиеся узлы и бакеты.
- При resize визуально объяснять, **откуда и куда** перемещаются элементы.
- В режиме дерева показывать настоящую древовидную форму, а не просто список с подписью `TREE`.
- Важные формулы и проверки показывать явно, не прятать всё за декоративными эффектами.
- Не создавать чрезмерную перегрузку: при большом количестве бакетов предусмотреть прокрутку, масштабирование, фокусировку или скрытие пустых бакетов с понятной индикацией.
- Продумать тёмную/светлую тему либо выбрать одну действительно качественную; обеспечить читаемость, адаптацию для широкого экрана и приемлемое мобильное представление.
- Анимация не должна блокировать управление навигацией по истории: быстрые нажатия и переключения шагов не должны ломать представление.

### Готовые сценарии (обязательны)

Пользователь должен запускать одним кликом демонстрации:

1. **Обычная вставка** — расчёт хеша → выбор бакета → вставка.
2. **Коллизия** — разные ключи попадают в один бакет, появляется/удлиняется цепочка.
3. **Обновление ключа** — `equals` находит существующий ключ, значение меняется, размер остаётся прежним.
4. **Resize** — превышение порога и split бакетов, включая пример, где часть цепочки остаётся, а часть переносится.
5. **Treeification** — многократные коллизии при достаточной ёмкости и переход в красно-чёрное дерево.
6. **Почему дерево не появилось** — большая цепочка при `capacity < 64` вызывает расширение вместо treeification.

Для каждого сценария должны существовать воспроизводимые Java-операции/входные данные, а не нарисованный заранее видеоролик. Желательно добавлять сценарии для поиска и удаления из дерева, когда соответствующая логика готова.

## 7. Тестирование и проверка поведения

**Корректность алгоритма важнее красоты анимаций.**

Минимальная проверка:

- Unit-тесты Java-ядра: индексация, spread hash, `null`, коллизии, поиск/обновление, удаление, загрузка/порог, resize, split, переход в дерево, работа дерева.
- Сопоставление результатов `put` / `get` / `remove` / `size` со стандартной `java.util.HashMap` на одинаковой последовательности операций (включая управляемые коллизии); полезны и детерминированные, и псевдослучайные сценарии.
- Проверка инвариантов структуры после завершённых операций: каждый ключ присутствует ровно один раз; правильные бакеты; связи корректны; красно-чёрное дерево удовлетворяет свойствам балансировки.
- Тесты trace: шаги упорядочены, полезные события действительно возникают, последний snapshot совпадает с финальным состоянием движка, ID узлов стабильны в ожидаемых переходах.
- API-тесты на контракты и независимость сессий.
- Минимальный end-to-end сценарий в браузере: создать сессию → вставить → увидеть trace → перейти назад/вперёд → запустить сценарий коллизии/resize.

Не выдавать упрощённую реализацию дерева за точную, если соответствующая логика не завершена. В таком случае в итоговом отчёте и UI честно обозначить ограничение.

## 8. Разработка, запуск, деплой

Репозиторий должен быть пригоден к запуску другим разработчиком:

- `README.md`: назначение, скриншоты по возможности, стек, структура проекта, быстрый локальный запуск, запуск тестов, описание учебной модели и ограничений.
- Воспроизводимая сборка с версиями зависимостей, удобные команды запуска Java backend и React frontend.
- Настраиваемый адрес API на фронтенде (`VITE_...` env или аналог), корректная конфигурация CORS для разработки и production.
- Не хранить секреты в репозитории; добавить `.gitignore` и пример переменных окружения, если нужны.
- Подготовить статическую сборку frontend для Netlify; backend должен отдельно собираться и запускаться как Java-сервис (например, контейнером).
- Цель развёртывания — **максимально дешёвый, предпочтительно бесплатный публичный демо-сайт**. Netlify подходит для фронтенда, но **не размещает обычный долгоживущий JVM/Spring Boot сервер**. Спроектировать раздельный деплой без привязки к конкретному провайдеру бэкенда; учесть возможные холодные запуски бесплатных хостингов.
- CI для сборки и тестов приветствуется, если не тормозит создание самого продукта.

## 9. Definition of Done: MVP

Считать первую версию готовой, если:

- [ ] Запускаются и взаимодействуют React frontend и Java 21 / Spring Boot backend.
- [ ] Операции над `HashMap` исполняются **Java-движком**, а не реализованы только в TypeScript.
- [ ] Пользователь может выполнить `put`, `get`, `remove`, reset и видеть корректный результат.
- [ ] Каждый значимый этап порождает событие и воспроизводимое состояние для анимации.
- [ ] Работают просмотр шагов назад/вперёд и play/pause.
- [ ] Визуально различимы пустой бакет, список с коллизиями и реальное дерево.
- [ ] Можно самостоятельно или готовым сценарием вызвать **resize** и **treeification**, а также случай resize вместо treeification.
- [ ] При resize видно перераспределение узлов между бакетами.
- [ ] Поведение критичных сценариев подтверждено тестами относительно OpenJDK 21.
- [ ] Приложение удобно на desktop, имеет понятные объяснения и не ломается при быстрых действиях.
- [ ] Есть README с локальным запуском, тестами и принципом раздельного деплоя.

## 10. Направление дальнейшего развития (не часть MVP)

- `ArrayList`: capacity, рост массива, сдвиги при insert/remove.
- `LinkedList`: node pointers, вставки и удаление.
- `HashSet` и `LinkedHashMap`: повторное использование логики HashMap, порядок элементов.
- `TreeMap` / `TreeSet`: деревья и сравнители.
- `ArrayDeque` / `PriorityQueue`: кольцевой буфер и двоичная куча.
- Режим сравнения двух реализаций, подсветка Java-псевдокода/исходника, учебные задания, сохранение и шаринг сценариев.

**Приоритет разработки:** сначала построить правильный и понятный событийный движок `HashMap`, затем хорошо его визуализировать, и только потом расширять набор коллекций.
